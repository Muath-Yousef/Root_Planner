# سجل الأدوار (Registry) — المرحلة 4

الأدوار هي لبنات الاستوديو: كل عقدة موظف أو بنية تحتية أو منطقة تستند
إلى `RoleDefinition` في السجل. هذا الملف يوثّق الأدوار المسجلة، وكيف
يُضاف دور جديد، وكيف تُوسَّع صلاحية دور — وهو **قرار موثّق، لا أثر
جانبي** لأي مرحلة.

## الأدوار المسجلة

| الملف | الأدوار | المصدر |
| --- | --- | --- |
| `src/registry/roles/command.ts` | المؤسس، المنسق، المدير | المرجع |
| `src/registry/roles/employees.ts` | المستطلع، السياق، المقيّم، الاستراتيجي، الصائغ، الامتثال، المراقب المالي، الحارس الأمني، مهندس الأنظمة، أمين المعرفة، محلل الأداء، أخصائي التكامل | المرجع (6) + مشتق (6) |
| `src/registry/roles/infrastructure.ts` | SSRFGuard، ذاكرات L1/L2/L3، بوابة الدفع، مناطق الشبكة | المرجع |
| `src/registry/roles/zones.ts` | مناطق الأقسام والشبكة | المرجع |
| `src/registry/roles/influencer.ts` | جامع البيانات، مختار المحتوى، صانع المحتوى | **مشتق** (منظومة المؤثرين v2/v3) |

تسجيل الأدوار في `src/registry/index.ts` (`registerRoles`) — نقطة
التوسيع الخاصة بالاستوديو: ملف `RoleDefinition` واحد + سطرا تسجيل.
بمجرد التسجيل يظهر الدور في القائمة (dock) والمفتش بصلاحياته المعلنة،
دون لمس أي كود واجهة.

## أدوار المؤثرين الثلاثة (منظومة v2/v3)

| الدور | المنح (grants) | المحظورات (prohibitions) | ماذا يعني ذلك عملياً |
| --- | --- | --- | --- |
| `collector` (جامع البيانات) | `model:invoke`، `task:read`، `task:complete` | `web:*`، `external:*`، `funds:*`، `storage:audit_modify` | يجمع بيانات المرشحين ويودعها في الذاكرة الخام L1 فقط؛ لا ويب، لا L2/L3 |
| `content_selector` (مختار المحتوى) | نفس المنح | نفس المحظورات | يختار زاوية المحتوى من زوايا الاستراتيجي وملف صانع المحتوى؛ لا يكتب الملف ولا يصوغ |
| `creator` (صانع المحتوى) | نفس المنح | نفس المحظورات | يجسّد الشخصية ويؤدي النصوص المصوغة للمراجعة البشرية؛ لا يختار المجال/الشخصية/اللغة/المنصة (قرارات مؤسس لم تُحسم) |

الصلاحيات **أدنى حد مقصود** (`source: 'derived'`). قواعد الاستوديو
التي تحكمها (`src/engine/permissionStore.ts`): المحظورات أولاً، ثم
المنح، ثم الرفض الافتراضي للأدوار غير المعروفة. `memoryPermitted` يسمح
بـ L1 دائماً (ذاكرة عمل مهمة)، ويطلب `storage:state_read/write` لـ L2
و`storage:vector_read/write` لـ L3 و`audit:read/write` لـ L4. مدقق
الكابلات (`checkCable`) يرفض أي كابل `MEMORY_BUS` إلى طبقة لا يملك
الدور صلاحيتها، وأي `EGRESS_NETWORK` من موظف بلا `web:read`.

ملاحظة عن البناء: ملف v3 المسلَّم يبني عقد هذه الأدوار بالفرع الحرفي
للمترجم (ترتيب مفاتيح `label, kind, role, networkMode, status,
employee`)، بينما `templateNodeData` يصدر `status` قبل `networkMode`.
لذلك تبقى مواصفة v3 تعلنها في `roles.custom` — والمترجم يقبل الإعلان
**فقط** حين يطابق التعريف الممرَّر التعريف المسجّل تماماً، ويرفض أي
تعريف متعارض (انظر `src/dsl/compiler.ts`). مصدر الحقيقة واحد: هذا
الملف؛ واختبار الانحراف في `tests/influencers-v2-build.test.ts` و
`tests/influencers-v3-build.test.ts` يحرس تطابقه مع النسخ الحرفية في
المولّدين.

## كيف يُضاف دور جديد

1. أنشئ ملف `RoleDefinition` في `src/registry/roles/` (انسخ بنية
   `influencer.ts` — عقد `employee` كامل: المهمة، النطاق، الاستثناءات،
   الأدوات، السياسات، التشغيل، موجّه الهوية، المهارات، بطاقة التقييم).
2. سجّله في `src/registry/index.ts`: استيراد + `registerRoles(...)`.
3. شغّل الاختبارات (`npm test`) — اختبار `schemas.test.ts` يتحقق أن كل
   دور موظف يولّد عقداً وبياناً (manifest) يطابقان المخططين، واختبار
   `topology.test.ts` يثبّت عدد أدوار الموظفين.
4. تحقق من الخرائط القائمة (`npm run cli -- validate
   examples/influencers_system_v3.socroot.json`) — التسجيل يجب ألا
   يغيّر أي بصمة مسلَّمة.

## مسار توسيع الصلاحية (قرار موثّق)

توسيع صلاحية دور — مثلاً منح `collector` قراءة L2 — لا يحدث ضمناً
أبداً. المسار:

1. **عدّل المنح في ملف الدور نفسه** (`src/registry/roles/influencer.ts`):
   أضف المنحة إلى `permissions.grants`، وأزل من `permissions.prohibitions`
   ما يتعارض معها (المحظورات تُفحص أولاً — منحة تحت محظور `web:*`
   مثلاً لا تعمل أبداً). إن كان المنح مستنداً إلى المرجع غيّر
   `source` إلى `'reference'` مع ذكر القسم؛ وإلا أبقه `'derived'`.
2. **سجّل القرار** في رسالة الـ commit (أو طلب الدمج): أي دور، وأي
   منحة، ولماذا، وما الذي يسمح به الاستوديو بعدها.
3. **أعد التحقق**:
   - `npm test` — اختبار الانحراف يرفض أي تعريف لا يطابق المولّدات،
     واختبار المخططات يرفض أي كابل يخرق القواعد.
   - `npm run cli -- validate examples/influencers_system_v3.socroot.json`
     — الخرائط القائمة يجب أن تبقى 0 أخطاء.
   - إن غيّرت المنح ما يسمح به كابل قائم (مثلاً كابل `MEMORY_BUS`
     إلى L2 كان مرفوضاً فأصبح مقبولاً)، فذلك تغيير سلوكي يستحق
     اختباراً يسمّيه — لا تمريراً صامتاً.
4. **ما الذي يسمح به الاستوديو بعد التوسيع** (أمثلة):
   - `storage:state_read` → `MEMORY_BUS` قراءةً إلى L2 مقبول
     (`memoryPermitted` يعيده صحيحاً)؛ بلا `storage:state_write`
     تبقى الكتابة إلى L2 مرفوضة.
   - `web:read` → `EGRESS_NETWORK` إلى SSRFGuard مقبول *بشرط* وجود
     الكابل ووضع شبكة غير `none` — المنحة وحدها لا تنشئ كابلاً ولا
     تغيّر وضع الشبكة.
   - `funds:*` → لا شيء تلقائياً: أي التزام مالي يبقى مشروطاً
     بتوقيع المؤسس (قاعدة الحوكمة)، والمنحة هنا استثناء يجب أن
     يسمّيه القرار صراحةً.
5. **ما لا يفعله التوسيع:** لا يغيّر ملفات `.socroot.json` المسلَّمة
   (بصماتها ثابتة)، ولا ينشئ كابلات، ولا يغيّر `roles.custom` في
   مواصفة v3 — إن تغيّر تعريف مسجّل وجب تحديث النسخة الحرفية في
   مولّد v2/v3 معه، وإلا رفض اختبار الانحراف.

## سطر الأوامر (CLI)

أوامر الطرفية في `src/cli/` (`npm run cli -- …`):

| الأمر | ماذا يفعل |
| --- | --- |
| `validate <file>` | يتحقق من `.socroot.json` أو YAML بـ `parseProjectText` و`checkCable` و`collectProblems`؛ خروج 0 عند 0 أخطاء (التحذيرات لا تُفشل) |
| `build <spec.yaml> [--out <file>] [--now <iso>]` | يترجم YAML إلى `.socroot.json`؛ حتمي حين يكون `created_at` مثبّتاً في المواصفة أو حين يُمرَّر `--now` |
| `export <file> --out <file>` | يكتب نسخة قانونية موثقة من مشروع سليم (JSON أو YAML) إلى المسار المختار؛ يرفض مشروعاً فاشل التحقق |

ملفات الأدوار المخصصة في YAML (`roles.source`) تُحلّ نسبةً إلى جذر
المستودع أولاً، ثم إلى مجلد المواصفة؛ والـ CLI يمرّر تعريفاتها إلى
المترجم عبر خيار `customRoles` — المترجم نفسه لا يحمّل ملفات.
